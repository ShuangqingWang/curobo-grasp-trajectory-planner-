# 轨迹规划逻辑分析 — 发布第二版优化方案

> 本文是一份**完整、独立**的方案，描述抓取轨迹规划服务的全部设计。
> 阅读本文不需要任何其他文档作为前置。
>
> 单位约定：长度 **mm**，角度 **degree**，关节角在服务内部以 **rad** 传递。
> 位姿数组格式 `[x, y, z, rx, ry, rz]`，旋转约定 `R = Rz(rz) · Ry(ry) · Rx(rx)`。
> 变换记号 `T_A_B` 表示"把 B 系坐标转换到 A 系"。

# 第零部分　服务启动（service startup）

## 0.1 这一部分做什么

**一次性准备好两条流程所需的全部常驻资源，然后开放触发端口。**

启动完成后，每次触发只创建本轮上下文，不再加载模型、不再预热。
启动过程中任一步失败，服务**不宣布就绪**。

## 0.2 启动命令

```text
./build/OpenmindTrajectoryPlan config/grasp_planner.json
```

| 参数 | 作用 |
| --- | --- |
| `config/grasp_planner.json` | 启动配置（缺省即此路径） |
| `--dump-config` | 打印合并后的配置并退出，不启动服务 |
| `--once --input-dir input` | 单次运行：读 `input/` 执行一轮后退出，不开 TCP |
| `--log-root <目录>` | 覆盖 `app.json` 的 `log_root`，用于 `/var` 不可写的开发机 |

**GPU 规划服务由主进程自己拉起**，不单独启动，也不使用包装脚本。
主进程退出时一并停止 GPU 子进程。

## 0.3 启动步骤

```text
 C++ OpenmindTrajectoryPlan                         Python curobo_plan_service（子进程）
 ─────────────────────────                         ─────────────────────────────────
 S0 进程入口
 S1 会话目录与日志
 S2 相机、运动学、放置工位校验
 S3 读 flow 配置
 S4 拉起 GPU 子进程 ───────── 启动参数 ──────────► S4.1 生成末端 220 个棱线球
    stdout/stderr → curobo_service.log              S4.2 构造规划器（607 球，预分配体素缓存）
    每 100ms 探活，最长 300s                         S4.3 工作台/底座球一致性校验
                                                    S4.4 预热两条调用路径
    ◄──────────── ping 应答（设备、球数、参数）──── S4.5 监听 127.0.0.1:34567
    核对参数一致
 S5 流水线初始化（grasp 4 stage + trajectory 5 stage）
 S6 导出固定碰撞模型快照
 S7 触发路由初始化
 S8 开 TCP 0.0.0.0:9108 → service_ready=true
```

| 步 | 做什么 | 进程 |
| --- | --- | --- |
| S0 | 解析参数；切换到项目根目录；设进程名 `OpenmindTrajectoryPlan`；安装信号处理；加载并合并配置 | C++ |
| S1 | 创建会话目录 `<log_root>/<session_id>/`；初始化日志；写 `session.json`（`status=initializing`） | C++ |
| S2 | 初始化相机管理器（三路内外参）与设备管理器（机型运动学）；解析放置工位，校验 `FK(q_place)` 与放置法兰一致、`q_place` 在限位内 | C++ |
| S3 | 读 `config/base/pipeline/flow/grasp.yaml`、`trajectory.yaml` | C++ |
| S4 | 拉起 GPU 子进程，把 `trajectory.yaml` 中决定规划器构造的参数作为启动参数传入（见 0.4）；子进程输出重定向到会话目录；轮询探活直到就绪 | C++ → Python |
| S4.1 | 读 `app.json` → `end_effector`，按 2.5.8 生成 220 个半径 2.6mm 的棱线球 | Python |
| S4.2 | 加载机型模型 `model/aubo_i12h_curobo.yml`，挂本体 387 球 + 末端 220 球；按启动参数构造 IK 与轨迹优化器；按 0.4 的尺寸预分配体素缓存 | Python |
| S4.3 | 工作台实心与 `base_link` 球一致性校验（见 2.5.11），不一致直接退出 | Python |
| S4.4 | 预热**抓取段位姿目标**与**放置段关节目标**两条调用路径（CUDA 图捕获） | Python |
| S4.5 | 开始监听；此后才能应答 ping | Python |
| S5 | 按顺序创建并初始化启用 flow 的全部 stage（见 1.4、2.4 的"启动时准备"列） | C++ |
| S6 | 导出固定碰撞模型快照（`model_id`、本体球、末端球），供可视化与本体规划同源 | C++ |
| S7 | 初始化触发路由（输出目录、模型标识） | C++ |
| S8 | 启动触发 TCP 服务，宣布 `service_ready=true` | C++ |

### 失败处理

任一步失败：

```text
[service][启动] <步骤名> 失败: <原因>
  → session.json 写 status=init_failed 与原因
  → 停止 GPU 子进程（SIGTERM）
  → 进程返回 1，不开 TCP 端口
```

| 情况 | 结果 |
| --- | --- |
| 会话目录无法创建 | 只能打到终端 `stderr`，进程返回 1 |
| GPU 子进程在探活期间退出 | `cuRobo 子进程启动期间退出，状态=<code>`，详情见 `curobo_service.log` |
| 300s 内探活不通 | `等待 cuRobo 服务就绪超时` |
| ping 回报的参数与 `trajectory.yaml` 不一致 | `cuRobo 启动参数与配置不一致: <字段> 期望=<值> 实际=<值>` |

## 0.4 GPU 子进程的启动参数

决定规划器构造的参数**必须在启动时传入**。规划器在 S4.2 构造并预热后不可热切换；
若启动时用默认值、到首次 `set_world` 才下发配置值，两者不一致会使首次触发直接报错。

```text
<curobo_python> services/curobo_planner/curobo_plan_service.py
    --host 127.0.0.1 --port 34567
    --activation-mm 3.0
    --cache-voxel-size-mm 3.0
    --cache-dims-mm <X> <Y> <Z>
    [--enable-graph-planner]            ← 仅 enable_graph_planner=true 时追加
    --warmup-on-start
```

| 参数 | 来源 | 值 |
| --- | --- | --- |
| `curobo_python` | `config/grasp_planner.json` → `curobo_python` | Python 解释器绝对路径 |
| `--host` / `--port` | `trajectory.yaml` → `curobo.host` / `port` | `127.0.0.1` / `34567` |
| `--activation-mm` | `trajectory.yaml` → `curobo.collision_activation_mm` | 3.0 |
| `--cache-voxel-size-mm` | `trajectory.yaml` → `curobo.world_voxel_size_mm` | 3.0 |
| `--cache-dims-mm` | 由长方体可能的最大尺寸推出，见下 | |
| `--enable-graph-planner` | `trajectory.yaml` → `curobo.enable_graph_planner` | 当前不传（关闭） |

**体素缓存尺寸**按长方体的**最大可能尺寸**预分配，而不是固定立方体：

```text
X、Y：2 × CAP = 2 × 1405.6 = 2811.2 mm   → 938 格
Z   ：工作台底面 −1000 到 z_hi 上限
```

长方体 XY 受 CAP 约束、−Z 受工作台底面约束，因此最大尺寸可预先确定。
以样本 z_hi = 334.2 为例，Z 为 1334.2mm（445 格），缓存为 938 × 938 × 445 ≈ 3.9 亿格，
fp16 约 783 MB。**单轴格数必须 ≤ 1024**（见附录 A.4），启动时校验，超限直接报错。

**启动后核对**：ping 应答带回子进程实际使用的激活距离、图规划开关、体素缓存尺寸与球数，
C++ 与 `trajectory.yaml` 逐项比对，不一致按启动失败处理。

## 0.5 GPU 子进程的日志落盘

子进程的 stdout / stderr **重定向到会话目录**：

```text
<log_root>/<session_id>/curobo_service.log
```

每行带时间戳，模型加载、末端球生成、预热各步带耗时，使启动耗时可以逐步拆分。
子进程的崩溃栈也落在同一文件，启动失败时从这里排查。

## 0.7 启动耗时

以下为实测（会话 `20260921_011559_058`，当时配置为 10mm 体素、末端 96 球）：

| 环节 | 耗时 | 性质 |
| --- | ---: | --- |
| S0～S3 | ~6 ms | 实测 |
| S4 GPU 子进程拉起 → 探活通过 | **94.7 s** | 实测 |
| S5 流水线初始化 | 434 ms（其中标签缓存 403 ms） | 实测 |
| S6～S8 | ~26 ms | 实测 |
| **进程启动 → service_ready** | **~95.1 s** | 实测 |

S4 几乎占满全部启动时间，其内部拆分由 0.5 的 `curobo_service.log` 给出。
第二版配置（3mm 体素缓存、607 球）下的启动耗时**待实测**。

## 0.10 验收

| # | 验收项 | 判据 |
| --- | --- | --- |
| 1 | 启动方式 | 只用 `二进制 + 配置` 启动，GPU 子进程由主进程拉起 |
| 2 | 启动参数一致 | 子进程的激活距离、图规划开关、体素缓存与 `trajectory.yaml` 一致；首次触发不出现"无法热切换" |
| 3 | 参数核对 | 人为改错一项启动参数 → 启动失败并指出字段 |
| 4 | 体素缓存 | 按最大长方体预分配；单轴 ≤ 1024，超限启动报错 |
| 5 | 子进程日志 | 会话目录下存在 `curobo_service.log`，含时间戳与各步耗时 |
| 6 | 两路预热 | 位姿目标与关节目标两条路径均已预热；首次触发不含 CUDA 图捕获开销 |
| 7 | 失败处理 | 任一步失败：`session.json` 为 `init_failed`，GPU 子进程不残留，不开 9108 端口 |
| 8 | 就绪宣布 | `service_ready=true` 只在 S0～S8 全部成功后打印 |

# 第一部分　抓取标签生成（flow grasp）

## 1.1 这一部分做什么

**输入一个工件类型和它的位姿，输出一组基座系下的抓取候选位姿。**

不做逆解、不做碰撞检测、不做轨迹规划，**不使用 GPU**，全部计算在 CPU 侧完成。

本部分成功只代表**生成了候选**，不代表这些候选可达、无碰撞或可执行 ——
可达性与碰撞由后续部分判定。

## 1.2 输入与输出

| 类型 | 内容 | 来源 / 单位 |
| --- | --- | --- |
| 本轮输入 | 工件类型 `workpiece_type` | 触发请求，用于选择标签库 |
| 本轮输入 | 工件位姿 `T_B_O_target` | 4×4 矩阵，工件系 → 基座系，平移 mm |
| 本轮关联 | `request_id`、`generation_id` | pipeline 分配，两条 flow 共用 |
| 固定输入 | NPZ 标签、工件与文件映射 | `grasp.yaml`，启动加载并缓存 |
| 固定输入 | 夹爪宽度上限、坐标标定、退让量 | `app.json`，启动校验 |
| 输出 | `output/grasp_generation/grasp_result.json` | 本轮抓取候选结果 |

三路深度图随触发一同送达，但本部分不解码，原样留在本轮上下文里交给后续部分。

## 1.3 每个候选的内容

| 字段 | 含义 |
| --- | --- |
| `grasp_tcp` | 未退让的咬合中心 TCP 位姿 |
| `grasp_flange` | 未退让的法兰位姿 |
| `trajectory_grasp_tcp` | 沿 TCP 局部 −Z 退让 84 mm 后的 TCP 位姿 |
| `trajectory_grasp_flange` | 退让后的法兰位姿，**后续规划的目标** |
| `gripper_width` | 夹爪开口，单位 m |
| `score` | 离线标签分数，越大越好 |

结果按 `score` 降序排列，最多 10 组。

> **为什么规划目标是退让位而不是抓取位**：相机装在法兰上，夹爪直接压到咬合中心时
> 相机与工件距离过近。沿 TCP 局部 −Z 退 84 mm 给相机留出净空。
> 退让是**右乘 TCP 局部 Z 方向平移**，姿态不变，不是沿基座系 Z 轴平移。

## 1.4 四个 stage

| 编号 | Stage | 启动时准备 | 触发后执行 |
| --- | --- | --- | --- |
| 一 | `load_request` | 输入字段与校验规则 | 校验本轮工件类型、位姿、关联标识 |
| 二 | `load_grasp_labels` | 加载全部启用工件的 NPZ，校验、过滤、合并、稳定排序，建只读缓存 | 按工件取缓存，取本轮最多 10 组标签 |
| 三 | `compose_grasp_poses` | 校验标定方向、统一单位，初始化合成器与 −84 mm 退让参数 | 用本轮工件位姿合成四组位姿 |
| 四 | `write_grasp_output` | 准备输出目录、字段格式、原子写入 | 写本轮 JSON，发布结果 |

**缓存只保存与本轮工件位姿无关的标签**，不缓存上一轮的基座系候选位姿。
每次触发创建独立上下文，候选列表清空后重新生成；stage 实例与只读标签缓存持续复用。

启动配置声明支持的工件，若标签缺失、文件损坏或过滤后为空，**初始化即失败并指出
具体工件与文件**，不把问题留到业务触发时才暴露。固定配置或标签更新后，
须重新初始化相关资源再接任务。

## 1.6 步骤 1：读取与校验请求

> Stage `一 load_request`，全部检查在触发后执行。

1. 从 TCP 入口创建的本轮上下文取得 `workpiece_type`、`T_B_O_target` 与本轮标识。
   **客户端已读取 input 文件并发送完整内容，stage 不再读取 service 侧的旧 input 文件。**
2. 校验工件类型非空，且属于启动配置声明的支持范围。
3. 校验位姿为有限数值的 4×4 刚体变换：末行合法、旋转正交且为右手系，
   **不接受缩放或剪切**。
4. 保存本轮工件系到基座系的变换，交下一 stage。

失败日志须指出**缺失字段、未知工件或非法矩阵**；不继续读标签或生成位姿。

## 1.7 步骤 2：取得离线抓取标签

> Stage `二 load_grasp_labels`。启动加载并缓存，触发后按工件取用，**不重复打开 NPZ**。

### 启动时的标签处理

1. 按 `asset_root / object_directory / grasp_label / label_file` 定位文件。
   同一工件允许配置多个 NPZ。
2. 读取 `translations`、`rotations`、`widths`、`scores`，校验条目一一对应、形状正确、
   数值有限；平移与开口单位为 **m**，旋转为 3×3 矩阵。
   **损坏文件或非法结构直接报错，不缓存不完整结果。**
3. 过滤 `width <= 0` 或 `width > gripper_width_max_m` 的标签。
4. 合并同一工件的全部有效标签，按 `score` 降序**稳定排序**；
   同分时保持配置文件顺序及文件内原始顺序。
5. 缓存有效标签及统计：来源文件、原始数量、过滤数量、有效数量。

### 触发时

按工件读取缓存，取前 `candidate_count` 条。不足则使用实际数量，**不复制补足**。
无有效标签则本轮失败。标签分数**不在此阶段**换算成轨迹评级。

> **工件键名与目录名必须一致**：启动时以映射表的键名作为"支持的工件"列表，
> 触发时做字符串精确匹配。键名与其 `object_directory` 不一致时，
> 启动即报错，不把问题留到有人真发该工件才暴露。

## 1.8 步骤 3：合成抓取位姿

> Stage `三 compose_grasp_poses`。启动复用标定与合成器，触发后逐标签计算。

令 DB 为离线抓取标签坐标系，F 为法兰系，TCP 为咬合中心：

```text
T_B_TCP_original = T_B_O · T_O_DB · T_DB_TCP
T_B_TCP_planned  = T_B_TCP_original · TransZ(−84 mm)
T_B_F_original   = T_B_TCP_original · T_TCP_F
T_B_F_planned    = T_B_TCP_planned  · T_TCP_F
```

标签与固定标定中的米制平移**先转换为 mm**，再与本轮 `T_B_O` 相乘。

四个结果分别对应 `grasp_tcp`、`trajectory_grasp_tcp`、`grasp_flange`、
`trajectory_grasp_flange`，并保留标签的宽度与分数，**不改变候选排序**。

> **标定方向必须在启动时核定**：合成需要的是 `T_DB_TCP` 与 `T_TCP_F`。
> 若配置实际给出的是反向变换，须先求逆。
> **字段名可能与实际方向不符，必须依据标定定义核对，不能凭字段名猜测、
> 也不能未经核对就求逆。**

验证每个生成位姿数值有效；候选为空或变换非法时本轮失败。

## 1.9 步骤 4：发布抓取候选结果

> Stage `四 write_grasp_output`，触发后执行。

1. 组装合法 JSON，根级包含 `request_id`、`generation_id`、`workpiece_type`、`candidates`。
2. 每个 candidate 含 1.3 节的四组位姿、`gripper_width`、`score`，最多 10 个，保持降序。
3. **原子写入** `output/grasp_generation/grasp_result.json`，成功后才宣告本部分成功。
4. 后续部分读取该文件，校验请求与代次一致、候选有效后，取 `trajectory_grasp_flange` 规划。

**不得只凭目标文件存在就判断本轮成功。** 写入失败则停止后续流程并记录错误；
上轮文件即使仍在磁盘，也不能作为本轮输入。
JSON 中只存结构化结果，**不混入日志文本**。

本部分发布成功**不设置**轨迹 `ready=true`，后者由轨迹部分验收与发布决定。

# 第二部分　轨迹规划（flow trajectory）

## 2.1 这一部分做什么

**拿第一部分生成的抓取候选，联合规划出两段可执行的关节轨迹。**

| 轨迹 | 起点 | 终点 | 目标类型 |
| --- | --- | --- | --- |
| `photo_to_grasp` | 拍照位**六轴关节角**（本轮 `request.txt` → `T_base_flange_joint_angles_deg`） | 抓取**法兰位姿** | 位姿目标，需要 IK |
| `grasp_to_place` | 抓取轨迹**实际末点** `q_grasp` | 固定六轴 `q_place` | 关节目标，不求终点 IK |

**起点 `q_photo` 不是固定值，每轮从 `request.txt` 读取**；只有终点 `q_place`
是启动时加载的固定配置（`config/base/app.json` → `app.place`）。

**两段都通过才发布**，任一段失败则该候选作废、换下一个。

> 起点用关节角、终点用位姿的原因见 **附录 A.1**。

> **`q_place` 不转成位姿再求 IK**，否则可能解到另一个关节构型。
> `FK(q_place)` 只用于独立的位姿复核。

## 2.2 输入与输出

```text
输入：output/grasp_generation/grasp_result.json（最多 10 组候选，按分数降序）
        每组取 trajectory_grasp_flange 作为规划目标
      本轮主／左／右三路深度图
      本轮 request.txt 中的拍照法兰位姿 T_base_flange
      本轮 request.txt 中的 T_base_flange_joint_angles_deg（拍照法兰对应六轴角，即抓取段起点 q_photo）
      request_id、generation_id
      启动时加载的固定 q_place、放置法兰、相机标定、机型运动学、工作台几何

输出：output/trajectory_planning/
        joint_trajectory_photo_to_grasp.json     正式发布
        joint_trajectory_grasp_to_place.json     正式发布
        candidates/photo_to_grasp_cand{i}_rank{k}.json      全部候选，排查用
        candidates/grasp_to_place_cand{i}_grasp_rank{g}_rank{k}.json
        collision_cloud_B.bin                    下发 GPU 的点云（float32 xyz，mm）
        point_cloud_B.ply                        可视化点云（二进制）
        trajectory_manifest.json                 本轮清单
```

执行契约 `aubo_joint_path/v1`：两条轨迹**只给位置**，速度由行为树控制，
采样间隔固定 `0.025 s/点`。

## 2.3 整体流程

整条流程由 **C++ 主导**，只把"这一对起终点该怎么走"委托给常驻 GPU 服务。

- **步骤 [1/6]~[6/6]** —— C++ 侧的编排步骤
- **① ~ ⑤** —— GPU 服务内部步骤，只在步骤 [4/6] 与 [5.3.2] 里发生

```text
 C++ OpenmindTrajectoryPlan                      Python curobo_plan_service（常驻）
 ─────────────────────────                      ────────────────────────────────
【服务启动：一次准备，持续复用（详见第零部分）】
```

## 2.5 步骤 [1/6]：下发碰撞世界

> Stage `三 build_collision_world` → GPU 服务 `set_world` 命令。

### 2.5.1 坐标系与工作台

所有坐标均为**基座坐标系**。机器人基座安装在工作台上，**基座坐标系的 XOY 平面就是工作台顶面**。

| 项 | 值 | 来源 |
| --- | --- | --- |
| 工作台顶面 | z = 0 | `config/base/app.json` → `base_platform.positive_extent_xyz_mm[2]` = 0.0 |
| 工作台高度 | 1000 | `config/base/app.json` → `base_platform.negative_extent_xyz_mm[2]` = 1000.0 |
| **工作台底面（−Z 下界）** | **z = −1000** | 上一项取负 |
| 工作台 XY 范围 | X[−400, 400]　Y[−400, 400] | `base_platform.negative_extent_xyz_mm[0,1]`、`positive_extent_xyz_mm[0,1]` = 400 |

> 佐证：基座外壳网格 `base_link.STL` 的 z 范围为 [0, 61.8]，基座底面正好落在 z = 0。

**工作台是固定障碍：不参与长方体范围的确定，但落在长方体内的部分写入距离场作为障碍。**

> 写入工作台**不增加显存**：距离场是稠密网格，长方体内每一格都存一个距离值，
> 与该格是否为障碍无关。显存只由长方体的格子总数决定。

### 2.5.4 第一步：截断点云

**点云必须先截断，截断后剩下的点才参与长方体范围的确定。**

```text
z_hi = max(拍照法兰.z, 放置法兰.z)

保留点 p，当且仅当：
    |p.x| ≤ CAP
    |p.y| ≤ CAP
    −1000 ≤ p.z ≤ z_hi
```

### 2.5.5 第二步：确定长方体

```text
+X：x_hi = max(截断后点云.x_max, 拍照法兰.x, 放置法兰.x)
−X：x_lo = min(截断后点云.x_min, 拍照法兰.x, 放置法兰.x)
+Y：y_hi = max(截断后点云.y_max, 拍照法兰.y, 放置法兰.y)
−Y：y_lo = min(截断后点云.y_min, 拍照法兰.y, 放置法兰.y)
+Z：z_hi = max(拍照法兰.z, 放置法兰.z)
−Z：z_lo = max(−1000, 截断后点云.z_min)
```

−Z 的含义：截断后点云的最低点若高于工作台底面，下界取点云最低点；
若有点低于工作台底面（已在第一步切掉），下界取工作台底面 −1000。

**不外扩。**

### 2.5.6 第三步：体素化（3mm）

```text
体素边长  v = 3 mm
网格尺寸  n_i = ceil((hi_i − lo_i) / v)
网格原点  origin = 长方体中心 − (n − 1) / 2 × v      （0 号格的中心）

点云：   index = rint((p − origin) / v)，所在格置为障碍
工作台： 与长方体相交的部分整块置为障碍
```

`rint` 为"四舍六入五成双"。结果是一个与长方体同尺寸的**占据栅格**（每格一个布尔值）。

**3mm 体素的量化误差硬上界为 2.598mm**，推导见 **附录 A.3**。

### 2.5.7 第四步：建立 ESDF

由占据栅格计算**精确**欧氏距离变换（EDT），在 GPU 上完成，**分两遍**：

```text
第一遍（外部距离）：以"障碍格"为站点 → 每格到最近障碍格的距离，记为正
第二遍（内部深度）：以"自由格"为站点 → 障碍格到最近自由格的距离，取负
合成：障碍格取第二遍的负值，其余格取第一遍的正值
```

每一遍的核心是**并行带状算法（PBA）**，cuRobo 自带
`curobo._src.perception.mapper.esdf.edt_parallel_banding.ParallelBandingEDT`。
算法细节、站点打包格式与单轴 1024 格上限见 **附录 A.4**。

> ⚠ **符号约定不能反**：必须"障碍外为正、障碍内为负"。
> 反过来会让整个世界被当成实心，任何构型都判为碰撞。

> ⚠ **单轴格数上限 1024**。超限必须**显式报错**，不得静默算错。

**计算方式**：

1. **站点数组与 PBA 缓冲两遍共用。** 第一遍结束、距离写出后，同一块站点数组重新播种为
   第二遍的站点，PBA 对象（含其内部缓冲）只创建一次。
2. **播种与求距离按块进行。** 沿 X 方向每次处理约 200 万格：

   ```text
   对每一块：
       播种：   块内格子 → 是站点则写入打包坐标，否则写 −1
       求距离： 解码块内最近站点坐标 → 整数算平方和 → 开方 × 体素边长 → 写入输出
   ```

   - 本格坐标用三个一维序列靠广播参与运算，**不展开成整网格**
   - 坐标差与平方和在 int32 中计算（最大 3 × 1024² 不溢出），最后才转浮点
   - 结果**直接写成 fp16**，即交给规划器的最终格式
3. **边界情况**：长方体内无任何障碍 → 全部填 +10 m；全部为障碍 → 全部填 −10 m。

**显存**：整个建立过程中只有四块与网格同尺寸的数组：

| 数组 | 字节/格 | 用途 |
| --- | ---: | --- |
| 占据标记 | 1 | 两遍都用它区分内外 |
| 站点数组 | 4 | PBA 原地改写，两遍共用 |
| PBA 缓冲 | 4 | 算法内部需要，两遍共用 |
| ESDF 输出（fp16） | 2 | 最终结果 |
| **合计** | **11** | |

其余中间量只在块内临时存在（约 200 万格 × 数个 int32，量级几十 MB）。
建立完成后，**常驻的只有 fp16 输出，2 字节/格**。

> **规划器侧的体素缓存须按实际网格尺寸预分配**，不得按立方体预分配：
> 3mm 下 3m 立方体约 10 亿格、仅 fp16 就要 2 GB，而实际网格约 1.62 亿格。

**正确性**：与 CPU 精确欧氏距离变换（`scipy.ndimage.distance_transform_edt`）**逐格零差异**：
fp32 结果最大差 0，转 fp16 后 0 格不一致。

> 否则在实心工作台下这些球会永久判撞。

#### 末端碰撞球：只布在棱线上

末端按轴对齐长方体建模（挂载坐标系原点在法兰面）：

| Y | [−50, 50] | 100 | 夹爪厚度方向 |
| Z | [0, 200] | 200 | 沿工具轴，Z=0 是法兰面，Z=200 是夹爪尖端 |

1. **只在棱线上放球，不填面、不填内部**。球心直接落在棱线上（内缩 = 0）。
2. **近法兰（Z=0 面）的 4 条棱中间不放球**，只保留两端角点（角点由竖棱提供）。

   | 平行 Z（4 条竖棱，连接 Z=0 与 Z=200） | 4 | 200 | 40 |
   | 平行 X，Z=200（尖端侧） | 2 | 62 | 13 |
   | 平行 Y，Z=200（尖端侧） | 2 | 100 | 21 |

4. **球半径 2.6mm**，相邻球心间距 ≤ 5.2mm，保证棱上无缝覆盖。

### 2.5.9 激活距离（阈值）

```text
collision_activation_mm = 3.0
```

单个球的判撞条件：

```text
穿透量 = 球半径 + 激活距离 − d(球心)
穿透量 > 0  →  判定碰撞
```

> 激活距离是规划器的**全局参数**，**同时作用于本体 387 球与末端 220 球**。

### 2.5.11 安装处圆柱豁免区 —— 当前关闭

> **当前状态：关闭。** 配置 `base_platform.installation_exclusion.enabled = false`。

**关闭时的行为**：工作台按**实心**栅格化，顶面以下全部为障碍。

**开启后的行为**：在工作台安装处挖掉一个有限直径、有限深度的圆柱（当前参数
⌀300mm × 深 50mm，从顶面向下）。体素形式下挖孔就是少填若干格子，**没有额外查询成本**。

**为什么关闭**：`base_link` 已移除全部探入工作台的球，不再需要挖孔。

> **这两者是二选一，不能都不要。** 启动时有强制一致性校验：
> 若 `enabled = false` 而 `base_link` 仍有球面探入工作台，**直接报错并指出球数与最低点**。
> 这种配错 GPU 不会报错，只会让每个构型都判撞、表面看像"目标够不着"，极难定位。

### 2.5.14 碰撞世界如何被规划使用

`set_world` 之后，GPU 服务持有的不是"点云"，而是三样常驻状态：

1. **ESDF 体素网格**（fp16，本节建好的那张距离场）—— 环境侧
2. **机器人碰撞球模型**（本体 387 + 末端 220，共 607 个）—— 机器人侧，
   启动时已挂在各连杆坐标系下，随关节角做正解移动，不随 `set_world` 变化
3. **场景碰撞检查器**（`scene_collision_checker`）—— 持有 ESDF 网格的引用，
   提供"给一批球心坐标，批量返回距离 + 梯度"这个接口

**世界模型只在这一层被替换**：`set_world` 调用 `motion.update_world(scene_cfg)`，
只换掉场景碰撞检查器里的 ESDF 网格张量；机器人的 607 个球的相对位置、IK
求解器、轨迹优化器**都不重建**。这就是为什么 `world_key` 相同时能跳过重建、
不同时只需要"换一张距离场"而不是重新初始化整个规划器（2.5.12）。

之后 [4/6] 的批量 IK、图规划、轨迹优化**三者调用的是同一个碰撞检查器**，
区别只在于"用它检查谁"：

| 调用方 | 查询对象 | 查询时机 |
| --- | --- | --- |
| 批量 IK（2.8 ①） | 候选关节构型的正解球位置 | 每次迭代（IK 是优化过程，非单次求解） |
| 图规划（2.8 ③，关闭时不涉及） | 候选路径点、以及路径点之间离散采样出的中间构型 | 构建/搜索图时 |
| 轨迹优化（2.8 ④） | 每个优化时间步的正解球位置 | 每次优化迭代 |

从 `set_world` 到最终交出轨迹，**全程只有这一张 ESDF 网格**，没有切换或近似。

## 2.8 步骤 [4/6]：请 GPU 交出多条候选轨迹

> Stage `四 plan_full_cycle` → GPU 服务 `plan` 命令。

一次请求交出**最多 4 条**收敛轨迹（`return_trajectories: 4`），GPU 内部五步：

### ① 批量 IK

32 个种子并行求解，请求 4 个解。**IK 带碰撞约束** —— 解出的构型若与场景碰撞会被淘汰。
全部不收敛则该候选失败，失败步记为 `ik`。

**碰撞世界在这一步怎么用**：IK 不是"先解出关节角再检查碰不碰"，而是把碰撞代价
直接加进 IK 的优化目标：

```text
目标 = 位置误差 + 姿态误差 + 碰撞代价 + 关节限位代价
```

碰撞代价的算法：给定一组候选关节角 → 对本体 387 + 末端 220 个球做正解，
得到 607 个球心的基座系坐标 → 每个球心查一次 ESDF（三线性插值，见附录 A.2）
→ 按 2.5.9 的穿透量公式算代价 → 全部球求和。32 个种子并行做梯度迭代，
每次迭代都重新算一遍上面这整套（正解 → 607 次插值查询 → 求和 → 求梯度），
直到收敛或到迭代上限。收敛后还会再做一次穿透判定：若代价仍大于 0，该种子
记为不收敛，即便位置/姿态误差已经达标。

自碰撞不查 ESDF：607 个球两两（排除相邻连杆的免检对）比较球心距离，
`球心距 < 两半径之和` 记为自碰撞代价，同样加进这个优化目标。

### ② 种子补位

收敛数不足 4 个时，复制一个成功解补齐，使后续优化仍有 4 条种子并行。

### ③ 图规划（PRM）—— 当前关闭

> **当前状态：关闭。** 配置 `curobo.enable_graph_planner = false`。

**关闭时的行为**：不构造 PRM 图规划器，本步骤不生成几何路径种子，
`[4.3]` 编号保留，日志打 `图规划=未启用（配置关闭）` 或 `无图规划器，跳过`。
同时压时重磨参数取 `finetune_attempts = 1`、`finetune_dt_scale = 0.55`。

**开启后的行为**：先用 PRM 搜一条"歪但不撞"的几何路径作为优化起点，
压时重磨参数改为 `finetune_attempts = 3`、`finetune_dt_scale = 0.75`。
这两者在 cuRobo 内部是绑定的。

**为什么关闭**：图规划是**兜底手段，不是必经步骤**。
cuRobo 官方默认第 0 次尝试**不跑**图规划，失败后才启用它。
本项目场景下，关闭后产出的轨迹与开启时**完全一致**，只是同一目标内的
收敛候选数从 2~4 降到 1~2；外层仍有最多 10 个抓取候选兜底。

> 置 `true` 可完整恢复图规划行为，用于回归对比。
> 该开关**同时作用于抓取段与放置段**。

**碰撞世界在这一步怎么用**：PRM 在关节空间里撒一批随机构型作为图节点，
两节点连一条边前先检查这条边是否可行——把边等间隔离散成若干个中间构型，
对每个中间构型做正解 → 607 球查 ESDF + 自碰撞（与 ① 同一套算法），
全部不穿透才算这条边无碰撞、留在图里。搜出一条节点序列后，把对应的
关节角序列交给 ④ 作为初始猜测（`seed_traj`），不再是 ② 里"复制成功解"
那种平凡种子，而是一条已经绕开障碍的粗糙路径。

### ④ 轨迹优化

4 条种子并行优化，带压时重磨。全部不收敛则该候选失败，
日志附带最小位置误差与姿态误差。

**碰撞世界在这一步怎么用**：轨迹优化把整条轨迹表示成一组优化时间步
（数量小于最终 `dt=0.025s` 的密度），对每个时间步同样做"正解 607 球 →
查 ESDF + 自碰撞 → 代价与梯度"，再加上平滑代价（速度/加速度/加加速度
连续性）、动力学限位代价，一起用梯度迭代优化整条轨迹，直到代价降到
收敛阈值以下。

**"压时重磨"具体重算的是什么**：第一遍优化收敛后，用一个更短的时间总长
（乘 `finetune_dt_scale`，关闭图规划时 0.55、开启时 0.75）重新跑一遍
同样的"正解 → 查碰撞 → 求梯度"流程，把轨迹往"更快执行、同样不碰撞"的
方向再磨一遍；`finetune_attempts` 就是这次重磨允许失败重试几次
（关闭图规划时 1 次，开启时 3 次——开启时有更好的初始路径，值得多磨几次）。

### ⑤ 稠密插值

按 `dt = 0.025 s` 插值并逐条裁剪，输出按 cuRobo 自身代价排序的多条轨迹。

**碰撞世界在这一步不参与**：插值只是把优化后的稀疏时间步按 `dt=0.025s`
重采样成稠密轨迹，纯数值插值，不再查 ESDF、不再算碰撞代价。

> 🔴 **cuRobo 的排序与本工程的评级无关。** 它按"精确到位 + 平滑省时"排序，
> 实测会把绕行 8.6 倍、高出拍照点 1.28m 的轨迹排在第 2 名。
> **调用方必须自己逐条评级，不能直接取 rank1。**

全部候选轨迹落盘到 `candidates/`，供排查用。

## 2.9 步骤 [5/6]：逐条筛选

> Stage `四 plan_full_cycle`，仍在同一候选循环内。

按 rank 逐条处理。抓取段通过 5.1 与 5.2 后进入 5.3 规划放置段；
放置段全部候选失败则尝试下一抓取 rank。**两段均通过才采用**，后面的不再计算。

### 5.1 三项评级

三项各自出 A / B / 丢弃，**整条取最差的那一档**。

| # | 指标 | A | B | 丢弃 |
| - | --- | --- | --- | --- |
| 1 | 路径倍率 = 法兰实际路径长 ÷ 两端直线距离 | ≤ 1.5 | ≤ 2.0 | > 2.0 |
| 2 | 抬升 = 轨迹法兰最高点高出拍照点的量 | ≤ 5 mm | ≤ 10 mm | > 10 mm |
| 3 | J1~J6 单轴净转角的最大值 | ≤ 180° | ≤ 360° | > 360° |

第三项的定义：

```text
单轴净转角 D_j = |q_j(终点) − q_j(起点)| ,  j = 1…6
评级指标    D   = max(D_1 … D_6)
```

使用**保留实际圈数**的连续关节角，不按 360° 取模。

> 某轴先 +100° 再 +100°，净转角 200°；先 +100° 再 −80°，净转角 20°。
> **本指标不统计中途往返**：先 +200° 再 −200° 的净转角为 0°，
> 因此它**不能**用来判断所有中途绕行。

> 抬升判据的数值容差取 **1 微米**（`lift_numerical_epsilon_mm: 0.001`）：
> 正解浮点噪声在 1e-5 mm 量级，机器人重复定位精度在 ±50 微米量级。
> 容差过小会把浮点噪声判成违规，导致候选被误杀。

### 5.2 运动学复核

GPU 已查过环境碰撞与自碰，这里只查三项，作为**独立于 GPU 的安全冗余**：

| # | 检查项 | 判据 |
| - | --- | --- |
| 1 | 净转角复核 | 任一轴净转角 > `max_redundant_joint_travel_deg: 360°` 失败 |
| 2 | 端点吻合 | 首/末点正解出的法兰 vs 期望法兰 |
| 3 | 关节限位 | 六轴都在机型限位内 |

**统一端点标准：位置 ≤ 1.0mm、姿态 ≤ 0.2°，两项均须通过。**
GPU 侧的收敛判据取同一组数值。

位置误差取三维欧氏距离，姿态误差取相对旋转角。
**最终发布以 CPU 复核为准；GPU 通过而 CPU 不通过时，记录双方误差并拒绝该条轨迹，
不自动放宽阈值。**

### 5.3 放置段

起点取抓取轨迹**最终优化、插值后的末点** `q_grasp`，**不能取优化前的 IK 种子**。

| 子步 | 内容 |
| --- | --- |
| 5.3.1 | 起终构型校验（关节限位由 CPU 独立复核） |
| 5.3.2 | 关节目标规划（图规划状态同 2.8 的 ③） |
| 5.3.3 | 插值，逐条裁剪 |
| 5.3.4 | 放置评级 |
| 5.3.5 | 放置复核 |

放置段评级规则：

| 指标 | 规则 |
| --- | --- |
| 法兰路径倍率 | 同抓取段 |
| 六轴首末净转角 | 同抓取段 |
| 抬升 | **不适用**，放置段允许向上运动 |

放置段复核除法兰端点外，另查**关节端点**：

- 放置首点关节角 = 抓取末点
- 放置末点关节角 = 指定 `q_place`
- 使用独立参数 `endpoint_joint_tolerance_deg: 0.5`，**不能用法兰姿态 0.2° 代替**
- 关节差**保留实际圈数**，不把差 360° 当作同一构型

> 固定起终关节角后，放置候选的净转角基本相同，**此项无法区分中途绕行**。

### 搜索顺序

```text
当前抓取 rank 通过 5.1 与 5.2
  → q_grasp = 抓取轨迹最后一点
  → 规划 q_grasp → q_place
  → 按放置 rank 评级与复核
      ├─ 当前放置 rank 失败 → 下一放置 rank
      ├─ 放置候选全部失败   → 下一抓取 rank
      └─ 放置 rank 通过     → 采用完整周期，结束搜索
抓取 rank 全部失败 → 下一抓取候选
候选耗尽或预算耗尽 → ready=false
```

> **两段都在同一次触发中预先规划**，不等真机夹取后才开始规划放置段。

| --- | --- | --- |

> 点云只供可视化，**执行轨迹并不需要它**；归档只供事后排查。两者都不该让客户端等。

# 附录　原理

## A.1 为什么起点必须是关节角、终点是位姿

机器人此刻就站在起点，姿态是**确定的**，只能用关节角描述；终点只知道"手要伸到哪"，
用什么姿势到达由规划器决定。

一个法兰位姿对应**最多 8 组逆解**（肩左/右 × 肘上/下 × 腕翻转）。若用位姿当起点，
规划器只能挑其中一组，而机器人实际停在哪一组并不确定。选错分支时，规划出的首点
与机器人真实构型不符，执行时机器人会先"跳"到首点 —— **那一跳不经过碰撞检测**，
且可能是大范围翻转。

## A.2 碰撞球如何查询 ESDF

### ESDF 是什么

**E**uclidean **S**igned **D**istance **F**ield，欧氏有符号距离场：
长方体内每一格存一个数，表示**该格到最近障碍表面的直线距离**。

| 位置 | 值 |
| --- | --- |
| 障碍外 | **正**，越远越大 |
| 障碍表面 | 0 |
| 障碍内 | **负**，越深越负 |

一维示例（障碍占 30~50mm）：

```text
位置 mm:   0    10    20    30    40    50    60    70
ESDF   :  30    20    10     0   -10     0    10    20
```

### 单个球的查询

对半径 r、球心 c 的碰撞球：

1. 找到球心所在的 8 个相邻格子。
2. **三线性插值**得到距离 `d(c)`，同时得到解析梯度 `∇d(c)`。
3. 计算 `穿透量 = r + 激活距离 − d(c)`。
4. 穿透量 > 0 时产生碰撞代价，梯度方向把球推离障碍。

**所有球都不穿透才算构型不碰撞。** 规划时它不只是"是/否"判断，
而是**代价 + 梯度**，IK 与轨迹优化都靠它把机械臂推离障碍。

自碰撞不查 ESDF，是不同连杆的球**两两比较球心距离**：`球心距 < 两半径之和` 即判撞。

### 为什么机器人只能用球表示

ESDF 给出的是"空间**一个点**到最近障碍的距离"。球是"到球心等距的点集"，所以：

```text
球面到障碍的距离 = d(球心) − 半径        ← 一次查询，精确
```

换成任何其他形状（如长方体），其到障碍的距离是"整个形状内所有点的 d 的最小值"，
无法一次点查询得到，只能在形状内采样多点 —— 而采样点加容差本质上又是球。
**机器人用球与环境用距离场是绑定的一对。**

### 插值不能消除量化误差

三线性插值让 ESDF 在格子之间连续、可求导，但它插的是"到**已被吸附到格心的**障碍"的距离。
点云在体素化那一步已经丢失的位置精度，插值无法恢复（见 A.3）。

## A.3 体素量化误差的硬上界

点云体素化时：

```text
index = rint((p − origin) / v)
```

真实点 p 落在格子内任意位置，被吸附到**该格中心**。每个轴上最大偏差为 `v/2`
（p 恰在两格中线上）。三轴同时取最坏值：

```text
误差上界 = √((v/2)² + (v/2)² + (v/2)²) = v · √3 / 2
```

即**半个体素的空间对角线**。

| 体素 v | 硬上界 |
| ---: | ---: |
| 10 mm | 8.66 mm |
| 5 mm | 4.33 mm |
| **3 mm** | **2.598 mm** |

该上界只取决于体素尺寸，与插值算法、碰撞球排布无关。

## A.4 并行带状算法（PBA）

### 结果与执行

| 项 | 内容 |
| --- | --- |
| 结果 | **精确**欧氏距离，非近似 |
| 执行 | GPU 上 5 次 kernel：FloodZ → MaurerAxis → ColorAxis → MaurerAxis → ColorAxis |
| 输入 | 站点数组：每格存"自身坐标"（是站点）或 −1（非站点） |
| 输出 | 同一数组被原地改写为"该格最近站点的坐标" |

### 站点打包

站点坐标按每轴 10 bit 打包进一个 int32：

```text
| 2 位未用 | 10 位 Z | 10 位 Y | 10 位 X |
```

10 bit 最多表示 1024 个值，故**单轴格数上限 1024**。这是数据结构决定的，不是可调参数。

### 由最近站点求距离

```text
d = √((x − sx)² + (y − sy)² + (z − sz)²) × 体素边长
```

### 为什么不用 TSDF 类方法

TSDF（深度图沿射线直接融合距离场）的表面定位中位误差可以更小，但在遮挡边界、
掠射角、深度跳变处会出现大偏差，并被截断距离钳住。实测同一份深度图、10mm 体素：

| | 占据栅格 + PBA | TSDF |
| --- | ---: | ---: |
| P50 | 4.93 mm | 3.09 mm |
| P95 | **6.91 mm** | 11.40 mm |
| 最坏 | **8.54 mm** | 40.00 mm |

占据栅格 + PBA 的误差**有硬上界**（A.3），可写入安全余量公式；TSDF 的尾部无界，无法对账。

## A.5 末端棱线覆盖的球数推导

一条棱是线段，两端各放一个球心（覆盖角点），中间按固定间距均匀排。要保证棱上任意一点到
最近球心的距离 ≤ 半径 r，相邻球心间距不能超过 `2r`：

```text
n ≥ 棱长 / (2r) + 1
```

r = 2.6mm，`2r = 5.2mm`：

| 棱长 | n ≥ | 取整 n | 实际间距 | 实际半间距 |
| ---: | ---: | ---: | ---: | ---: |
| 62 mm | 12.92 | **13** | 5.167 mm | 2.583 mm ≤ 2.6 ✓ |
| 100 mm | 20.23 | **21** | 5.000 mm | 2.500 mm ≤ 2.6 ✓ |
| 200 mm | 39.46 | **40** | 5.128 mm | 2.564 mm ≤ 2.6 ✓ |

少一个球即漏：例如 62mm 棱用 12 个球，间距 5.636mm、半间距 2.818mm > 2.6mm。

**角点去重**：长方体每个角同时属于 3 条棱。竖棱贯穿 Z=0 与 Z=200，两端恰为全部 8 个角点，
故竖棱按全数计入；其余棱只计中间点（扣除两端）。

## A.6 长方体之外视为不碰撞

规划器查询 ESDF 时，若球心落在网格之外，对该球返回"不碰撞"，**不报错**。

长方体按"截断后点云 ∪ 拍照法兰 ∪ 放置法兰"的包围盒确定，所有写入距离场的障碍都在长方体内。
但长方体**不外扩**，因此若某个球的球心恰在长方体外、而球面（加激活距离）已触及边界上的障碍，
该球不会被判撞。末端球的这一窗口为 `2.6 + 3 = 5.6mm`；本体球为 `本体球半径 + 3mm`。
